# 如何写清完成标准

“完成标准”回答的是一个朴素问题：做到什么程度，这次改动才算真的完成？

它不是为了增加文档，而是为了避免三种返工：目标理解错了、改动范围越做越大、测试通过了却不是用户想要的结果。

## 先按风险决定写多少

OpenOne 提供两种处理方式：

| 处理方式 | 适用情况 | 需要记录什么 |
| --- | --- | --- |
| 自动选择 | 默认方式；低风险任务自动使用轻量处理，发现风险就提高检查强度 | 按实际风险记录目标、范围、检查和最终结果 |
| 完整检查 | 系统性功能、高风险改动、准备合并或发布 | 完整的目标、范围、主要流程、失败情况、质量要求和验收项 |

新安装默认使用自动选择。旧工作区如果还没有 `workflow/policy.yaml`，继续做完整检查，避免升级后静默放宽原有规则。

无论采用哪种方式，远程推送、正式发布、部署、生产写入和对外动作都需要用户明确授权。

## 一份清楚的完成标准包含什么

| # | 要写清的内容 | 检查问题 |
| --- | --- | --- |
| 1 | 目标 | 用户最终能做什么？什么现象说明问题已解决？ |
| 2 | 改动范围 | 这次会改什么，不会改什么？哪些文件或系统不能碰？ |
| 3 | 现有行为 | 当前系统怎样工作？有没有已经上线的行为需要保持？ |
| 4 | 主要流程 | 数据从哪里来、经过什么步骤、最后到哪里？ |
| 5 | 失败情况 | 弱网、重试、并发、权限不足、中断或配额耗尽时怎么办？ |
| 6 | 质量要求 | 响应时间、包体、内存、成本或易用性有没有明确上限？ |
| 7 | 验收项 | 每条结果怎样检查？用什么命令或人工步骤？合格标准是什么？ |
| 8 | 需要确认的决定 | 是否仍有会改变实现方向的问题，需要用户选择？ |

不是每次都要填满八项。轻量处理只保留与当前改动有关的内容；完整检查才展开完整结构。无法量化的“快、稳定、流畅”等词，应改成可观察行为或明确数字。

## 轻量处理怎么完成一次小改

```text
用户提出改动
  → 确认会改什么
  → 集中完成修改
  → 查看改动是否符合目标
  → 运行针对性检查
  → 汇总结果和剩余风险
```

这条路径有三个限制：

1. 检查失败后最多进行两轮修复，避免无限循环。
2. 先查看改动，再运行最终检查，避免检查通过后又修改代码而重复全套验证。
3. 过程记录在结束时统一写一次，不在每个小步骤中反复同步。

如果中途发现接口、数据、权限、安全、迁移、生产配置、跨仓或不可逆风险，agent 会转为完整检查，并说明为什么需要补充完成标准。

## 完整检查怎么推进

```text
讨论需求
  → 必要时补充关键信息
  → 整理产品与界面要求
  → 评估技术方案
  → 准备检查清单
  → 用户确认完成标准
  → 开工前检查
  → 修改、审阅和验证
  → 准备发布
```

用户确认完成标准之后，如果目标、范围或验收方式发生实质变化，agent 应明确说明变化并再次确认，不能把新要求静默塞进原计划。

开始修改前的检查只负责找矛盾，例如产品说明允许某种行为，而技术方案或验收项却禁止它。发现会导致错误实现的矛盾时，应先修正文档；轻微措辞问题不应阻止工作。

## 如何写验收项

每条验收项至少包含：

- 要验证的结果；
- 自动检查命令或人工步骤；
- 通过标准；
- 当前结果；
- 能复查的证据，例如命令输出、退出码或截图路径。

普通用户看到的状态统一为：

| 状态 | 含义 |
| --- | --- |
| 未检查 | 还没有运行相应检查 |
| 已通过 | 证据满足通过标准 |
| 未通过 | 已检查，但结果不符合要求 |
| 改动后需重查 | 之前通过，但相关内容后来又被修改 |
| 已确认跳过 | 用户明确同意本次不检查，并保留原因 |

只有所有“必须通过”的验收项都已通过，或由用户明确同意跳过，agent 才能宣布完成。存在未检查、未通过或改动后需重查的必选项时，应直接说明还没有完成。

## 三类长期资料

| 资料 | 默认位置 | 用途 |
| --- | --- | --- |
| 项目基本规则 | `workflow/constitution.md` | 跨改动都不能违反的技术、安全和成本原则 |
| 个人开发规范 | `workflow/standards/` | 命名、错误处理、依赖选择等可复用约定 |
| 已上线功能说明 | `specs/` | 当前产品已经实现并发布的行为，是修改旧功能时的事实起点 |

路径、技术栈和资料位置放在 `workflow/team-profile.yaml`；默认处理方式和风险升级条件放在 `workflow/policy.yaml`。这样项目事实、长期规则、个人规范和已上线行为不会混在每次需求文档里重复讨论。

## 实用示例

### 轻量改动

需求：把设置页按钮从“保存”改成“保存更改”。

- 目标：设置页按钮显示新文案。
- 范围：只改按钮文字和受影响的界面测试，不改保存逻辑。
- 验收项：相关界面测试通过；搜索确认旧文案没有残留在这个页面。

### 高风险改动

需求：增加账号删除功能。

- 目标：用户完成二次确认后可以申请删除账号。
- 范围：账号页面、身份确认、删除任务和审计记录；不自动取消外部计费，除非另有决定。
- 失败情况：确认过期、任务中断、重复提交、部分数据清理失败。
- 质量与安全：必须再次验证身份；删除操作可追踪；敏感数据不写入普通日志。
- 验收项：授权、重复提交、失败恢复、审计记录和用户提示都存在可复查结果。
- 用户确认：数据保留期限和外部计费处理方式必须在实现前决定。

## 高级兼容信息

这一节说明旧版文件和内部状态怎样映射到新的用户语言。普通使用无需掌握。

### 文件与命令兼容

- “完成标准”目前仍写入 `features/<feature>/00-完成合同.md`，以兼容已有目录、模板和 `bin/check-contract.cjs`。
- `/定义完成` 的兼容 ID 不变，用户显示名称为“确认完成标准”。
- `/交付至完成` 的兼容 ID 不变，用户显示名称为“完成这次改动”。
- `/07-测试执行` 的兼容 ID 不变，用户显示名称为“验证改动”。
- 内部分级 `S / M / L` 分别显示为“轻量改动 / 常规改动 / 高风险改动”。

结构检查仍可运行：

```bash
node bin/check-contract.cjs features/<feature>/00-完成合同.md
```

### 旧术语映射

| 内部或旧版术语 | 默认用户语言 |
| --- | --- |
| Completion Contract / 完成合同 | 完成标准 |
| freeze / 冻结 | 完成标准已确认 |
| Oracle | 验收项 |
| blocking | 必须通过 |
| Oracle ledger | 验收记录 |
| Definition Lint | 完成标准检查 |
| gate | 开始条件或发布条件 |
| `NOT_RUN` | 未检查 |
| `PASS` / `FAIL` | 已通过 / 未通过 |
| `STALE` | 改动后需重查 |
| `WAIVED` | 已确认跳过 |

内部状态码继续用于机器读取和旧工作区兼容，默认对话和进度页不直接展示。只有用户要求技术详情、排障、审计或发布核验时，才展开原始 ID、状态码和证据字段。

## 设计参考

机制设计参考了 spec-driven 开发中的需求澄清、风险驱动测试、按规模调整流程、结构化需求和长期规范分层等做法。OpenOne 面向个人开发者的取舍是：低风险工作尽量短，高风险工作才补齐完整证据；流程强度跟随风险，而不是让每个小改都承担发布级成本。
