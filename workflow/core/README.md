# Workflow Core

`workflow/core` 定义与工具无关的处理步骤、模板和可复用检查。它不得包含公司特定业务事实、内部仓库名、私有 URL、凭证、客户数据或某个工具的私有能力。

工作区有两类工作：研发改动（`/new-feature`、`/01` 到 `/10`）和商业化工作（`/new-product`、`/B1` 到 `/B9`）。两类工作共享同一授权边界：范围清楚时，agent 可执行本地文档、代码和 Git 操作；远程写入、发布、部署、数据库写入和生产配置写入始终需要用户明确授权。

## 两种处理方式

- **自动选择**（内部值 `adaptive`）：低风险本地改动走“轻量处理”；碰到 API/数据结构、认证权限、迁移、持续集成与部署流程（CI/CD）、生产配置、跨仓、不可逆操作或改动超出范围时，立即升级。
- **完整检查**（内部值 `strict`）：先确认完成标准，再实现、验证和留存完整证据，适合系统性改动、高风险改动和合并/发布前检查。

处理方式由 `workflow/policy.yaml` 决定。新安装默认“自动选择”；旧工作区没有该文件时保持“完整检查”，避免升级后意外放宽。

完整检查以“完成标准”为判定依据：每个目标都有可重复的验收项，所有必须通过的验收项均已通过（或用户已确认跳过并记录风险）才能宣布完成。`workflow/constitution.md` 是项目基本规则，`workflow/standards/` 是代码规范，`specs/` 是已上线功能说明。

## 不会因处理方式改变的规则

- 同一套 core，多个工具 adapter 分层增强。
- 不承诺所有工具体验完全一致。
- 业务代码修改前必须确认当前请求已进入实现、分支正确，并检查未提交改动。
- 个人项目允许 agent 在范围明确且工作树已检查后执行本地分支命名、创建、commit、tag 和本地 merge。
- 远程 Git、push、GitHub release、商店提交、部署、数据库写入和生产配置写入必须获得用户明确授权。
- 只有同一仓库确实有多个需求并行实现时，才必须使用独立 worktree（独立开发目录）。
- adapter 可以增强或降级体验，但不能削弱上述安全底线。
- 商业化工作只产出文档和清单：对外发布内容、投放广告、主动联系陌生潜在客户、联系合作方必须用户明确授权或自行执行；需要修改代码的营销需求通过 `/new-feature` 进入研发部分，不在 B 阶段直接改代码。
- 商业化结论必须做证据分级（一手/二手/推断），不得编造市场数据、用户评价或竞品价格。
- 完整检查中，完成标准已确认后不得静默修改验收标准、阈值或“必须通过”标记；变更需记录并再次获得用户确认。
- 验收结果必须来自真实执行的命令、运行态证据或人工步骤；代码改后与之相关的旧结果必须重新验证。
- 需求与项目基本规则冲突时，先经用户确认修订基本规则，不得绕过。

## 内部兼容说明（默认不对用户展示）

为避免破坏现有工作区，目录和部分机器字段暂时保留旧名：`features/{feature}/00-完成合同.md`、`Oracle`、`Definition Lint`、`blocking`、`NOT_RUN/PASS/FAIL/STALE/WAIVED`。默认对话分别展示为“完成标准”、“验收项”、“完成标准检查”、“必须通过”和中文结果。只在排障、审计、发布或用户主动要求技术详情时展示内部名。

## 目录地图

- `commands/`: 每个阶段的契约。
- `templates/`: 通用文档模板。
- `capabilities/`: 可复用检查能力。

## 项目特化

不要为了加入单个项目事实而修改 core 文件。项目特化内容应放在：

- `workflow/team-profile.yaml`
- `features/{feature}/`
- 目标项目自己的规范和本地资料
- 工具 adapter 的薄入口
