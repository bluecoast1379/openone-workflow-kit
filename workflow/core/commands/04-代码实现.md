# /04-代码实现

## Goal

开始修改：先解析处理方式和开始条件，然后在已确认范围内完成代码、配置与必要测试改动。

## Required Inputs

- 用户的改动请求和已确认的改动范围
- 两种方式都读：`workflow/policy.yaml`、`workflow/team-profile.yaml`、直接相关的代码与仓库规则、当前分支和未提交改动
- 仅在完整检查或相关风险触发时读：`workflow/constitution.md`、`workflow/standards/`、`specs/`、`features/{feature}/00-完成合同.md` 及相关阶段文档

## Execution Rules

- 如果已安装策略解析器，在开始时运行 `node workflow/core/tools/resolve-policy.cjs --workspace . [--profile adaptive|strict] [--signal <id[,id...]>] [--changed-files <path[,path...]>]`，记录解析后的处理方式和升级原因。无解析器时按 `workflow/policy.yaml` 判断；策略文件也缺失时按“完整检查”执行。
- `/04`、`/04A`、`/04B` 和 `/交付至完成` **都是实现步骤**。不得因为使用 `/交付至完成` 而被错误阻止。
- 轻量处理的开始条件：用户已要求这次本地修改，范围与验收项清楚，未命中升级条件。不要求额外的需求文件夹、完成标准文件或完成标准检查。
- 完整检查的开始条件：完成标准已由用户确认，完成标准检查已通过，开始前的高风险不一致已解决。
- 写入前必须检查 `git status --short --branch`、当前分支和无关的用户改动。个人仓库中，agent 可在范围和未提交改动已检查后，从约定基线创建本地开发分支；不得覆盖、暂存或提交无关的用户改动。
- 只有同一仓库确实存在多个活跃需求并行实现时，才必须为本需求使用独立 worktree（独立开发目录）。范围和 dirty tree 已检查后，agent 可创建对应的本地分支与 worktree。
- 只修改已确认的范围。实现中一旦发现 API/数据结构、认证权限、迁移、持续集成与部署流程（CI/CD）、生产配置、跨仓、不可逆操作或改动超出范围，立即停止轻量处理，用对应 `--signal` 重新解析并升级为完整检查。准备合并或正式发布时传入 `--signal pre_merge_or_release`。
- 不得声称测试、构建、截图、部署或审查已通过，除非确实执行并保留了对应结果。
- 本命令授权范围内的本地修改和本地验证，不授权远程 Git、发布、部署、数据库写入、生产配置写入或其他对外动作。

## Required Outputs

- 轻量处理：不逐轮创建或同步多份文档；在最终结果中一次性记录改动、diff 审查、验证命令和未完成项。
- 完整检查：更新 `features/{feature}/` 中对应实现记录和 `00-工作流状态.md`。
- 任何明确卡点必须说明：缺什么、为什么需要、已尝试什么、建议如何解除。
