# Core Commands

每个命令文件定义一项处理步骤。工具可以把它们展示为 slash command、prompt、规则或检查表，但执行依据仍是这些 core 文件。

默认使用简体中文展示阶段沟通和产物；专有名词、产品名、品牌名、代码标识符、命令、文件路径、分支名、API、SDK、框架、协议、标准、错误信息和官方英文术语保留原文。

工作区包含两类工作，共享同一授权和安全口径：

- 研发改动（`features`）：根据风险选择轻量处理或完整检查，再推进到实现、发布和复盘。
- 商业化工作（`business`）：把一个产品从业务定位推进到渠道执行和策略复盘，资料放在工作区级 `business/{product}/`。B 阶段只产出文档和清单；对外发布、投放和主动联系陌生潜在客户需要用户明确授权，需要修改代码的营销需求通过 `/new-feature` 进入研发部分。

研发改动默认由 `workflow/policy.yaml` 选择处理方式：

- **自动选择**：符合低风险条件时只做范围检查、批量修改、diff 审查、定向验证和一次性结果记录；不要求建立需求文件夹、单独确认完成标准文件或逐轮同步多份文档。
- **完整检查**：建立改动记录，确认完成标准，运行完成标准检查，再实现、审查和完整验证。

下列情况必须自动升级为“完整检查”：对外 API 或协议、数据结构、认证或权限、迁移、持续集成与部署流程（CI/CD）、生产配置、跨仓、不可逆操作，或完整 diff 超出已确认范围。

研发轨 stages:

- `/init-workspace`
- `/new-feature`（开始一个改动）
- `/01-需求讨论`
- `/澄清`（按需：≤5 问消融歧义，答案写回文档）
- `/02-产品文档`
- `/02B-UI设计`（含体验预算）
- `/03-技术架构`（含数据流/状态机草案与规范提取）
- `/03-06-研发准备`
- `/06-测试用例`（按风险准备验收项）
- `/定义完成`（确认完成标准）
- `/一致性检查`（开始修改前检查）
- `/04-代码实现`
- `/04A-前端代码实现`
- `/04B-后端代码实现`
- `/05-代码审查`
- `/07-测试执行`（记录真实验收结果）
- `/交付至完成`（在范围内完成修改和验收，或停在明确卡点）
- `/08-发布准备`（所有必须通过的验收项均已通过后准备发布）
- `/09-发布执行`
- `/10-复盘总结`（回写 specs 行为基线）
- `/workflow-status`

推荐顺序：

- 轻量处理：确认范围 → 批量修改 → 审查 diff → 最终定向验证 → 一次性记录结果。
- 完整检查：`/new-feature` → `/01` →（`/澄清`）→ `/02` →（有新 UI 方案时 `/02B`）→ `/03` → `/06` → `/定义完成` → `/一致性检查` → `/交付至完成` 或 `/04`→`/05`→`/07` → `/08` → `/09` → `/10`。

## 内部兼容详情

内部仍可使用 `S/M/L`、`Oracle`、`Definition Lint`、`blocking`、`STALE`、`WAIVED` 等代码与旧文件协议，但默认用户界面和对话不展示它们。只在技术详情、排障、审计或发布证据中展开。

商业化轨 stages:

- `/new-product`
- `/B1-业务定位`
- `/B1-B8-商业化准备`
- `/B2-商业模式`
- `/B3-PMF与客户画像`
- `/B4-场景与购买旅程`
- `/B5-渠道漏斗映射`
- `/B6-营销获客策略`
- `/B7-营销预算`
- `/B8-渠道执行策略`
- `/B9-策略复盘`（周期执行）

两轨衔接点：`/01`、`/02` 读取 B1/B2/B3/B4 的定位、商业模式、ICP 与场景基线；`/08`、`/09` 对照 B5/B8 准备发布营销材料和分发清单；`/10` 的增长信号回流 `/B9`；B8 的营销工程需求通过 `/new-feature` 进入研发轨。

The initializer writes concrete command files into the target workspace.
