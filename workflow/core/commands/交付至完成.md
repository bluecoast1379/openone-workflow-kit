# /交付至完成

## Goal

交付至完成: 在合同冻结且全部闸门通过后，授权 agent 在合同范围内自主循环「实现 → 验证 → 修复 → 复验」，直到全部 blocking Oracle 为 PASS（可宣布完成），或停在一个精确阻塞点。这是"写清完成定义，agent 自己跑到全绿"的执行命令。

## Required Inputs

- `AGENTS.md`
- `workflow/team-profile.yaml`
- `workflow/constitution.md` 与 `workflow/standards/`
- Workspace-level `features/{feature}/00-完成合同.md`（状态必须为「已冻结」，Definition Lint 通过）
- 前序阶段文档与 `specs/` 现有行为基线

## 准入闸门（全部通过才可开始）

1. 完成合同已冻结且 Lint 通过（S 档：★ 节完整且无待澄清项）。
2. 功能分支闸门：在从 `prod` 创建的开发分支上，工作树干净或已刻意暂存。
3. 同仓并行闸门：多需求并行时已使用独立 worktree。
4. 建议先运行 `/一致性检查`，存在未解决的高危漂移时先修文档再开始。

## Execution Rules

- 循环语义：每轮 = 实现一个增量 → 运行受影响的 auto Oracle → 修复失败 → 复验；全部 blocking Oracle PASS 后做一次全量复验收尾。
- **范围铁律**：只修改合同影响边界内允许的部分；发现必须越界才能完成时，停下并作为阻塞上报，不得静默扩权。
- **标准铁律**：不得修改任何 Oracle 的标准、阈值或 blocking 标记，不得删除测试来换取通过；发现标准本身有问题时，停下并提出合同修订请求（走修订记录+用户确认）。
- Oracle 状态翻转必须附可复现证据（命令、输出、退出码、截图路径、日志片段）；PASS 后相关代码再次变更的 Oracle 置 STALE 并复验。manual Oracle 无法由 agent 独立判定时保持 NOT_RUN 并列入待人工验收清单，不算阻塞失败但计入未全绿。
- **内建对抗审查**：宣布全绿前，切换审查者视角对完整 diff 做一轮问题优先审查（对照合同影响边界、PRD 一致性、`05-代码审查` 的口径）；发现问题回到循环，审查结论写入交付日志。
- 迭代与止损：同一 Oracle 连续 3 轮修复仍 FAIL，停下并上报精确阻塞（差距、已尝试路径、建议选项），不做无限循环。
- 授权边界：本命令授权本地代码修改、本地测试构建、本地 commit（范围明确时）；**不授权** push、release、部署、数据库写入、生产配置写入或任何对外动作。
- 精确阻塞的标准格式：缺什么（凭据/决策/环境/信息）、为什么需要、建议的解除路径；不得用"遇到困难"之类模糊表述。
- 默认使用简体中文展示工作流沟通和阶段产物；专有名词、代码标识符、命令、文件路径、分支名、API、SDK、框架和官方英文术语保留原文。
- Do not claim tests, builds, screenshots, deployments, or reviews passed unless they were actually executed.

## Required Outputs

- Create or update workspace-level `features/{feature}/交付至完成.md`：逐轮记录（改动摘要、运行的 Oracle、状态翻转、证据、审查发现、修复），终态结论（全绿 / 待人工验收清单 / 精确阻塞）。
- 同步更新 `features/{feature}/00-完成合同.md` 的 Oracle 状态表（含证据与时间）。
- Update workspace-level `features/{feature}/00-工作流状态.md`：交付模式记为「交付至完成」，`04/05/07` 阶段标注「由交付至完成覆盖」并链接交付日志。
- 终态为全绿时，输出给用户的验收摘要：合同目标逐条对照、Oracle 全表、待人工验收项、遗留假设。
