# /交付至完成

## Goal

完成这次改动：在已确认范围内自主实现、审查和验证，直到验收项全部满足，或停在一个能够具体处理的明确卡点。

## Required Inputs

- 用户的改动请求、已确认的范围和验收项
- 两种方式都读：`workflow/policy.yaml`、`workflow/team-profile.yaml`、直接相关的代码与仓库规则、当前分支和未提交改动
- 仅在完整检查或相关风险触发时读：`workflow/constitution.md`、`workflow/standards/`、`specs/`、`features/{feature}/00-完成合同.md` 与前序记录

## 开始条件

1. 先运行已安装的策略解析器（或具有相同语义的工具）：

   ```bash
   node workflow/core/tools/resolve-policy.cjs --workspace . [--profile adaptive|strict] [--signal <id[,id...]>] [--changed-files <path[,path...]>]
   ```

   以它输出的 `resolved_profile` 为准，记录 `policy_source` 和 `escalation_signals`。解析器不存在时按 `workflow/policy.yaml` 判断；策略文件也缺失时按“完整检查”执行。
2. 检查当前分支和未提交改动，保留与本次无关的用户改动。轻量处理遵循仓库已有分支策略，不强制为每个小改新建分支；完整检查按 `team-profile` 中明确配置的分支规则执行。
3. 同一仓库确实有多个活跃需求并行实现时，使用独立 worktree（独立开发目录）；无真实并行时不额外创建。
4. 轻量处理：用户的改动请求即是本地实现授权，不要求完成标准文件。完整检查：完成标准必须已由用户确认，且完成标准检查通过。

## 自动升级

实现前或实现中发现以下任一情况，立即停止轻量处理，传入对应 `--signal` 重新解析，并转为“完整检查”：

- 对外 API、公开协议或外部集成约定；
- 数据结构、持久化格式或兼容性；
- 登录认证、授权、权限或安全边界；
- 数据迁移、表结构迁移或批量修复；
- 持续集成与部署流程（CI/CD）、发布触发条件、部署脚本、基础设施或运行环境；
- 生产配置、密钥或真实生产数据；
- 跨仓库改动；
- 不可逆或难以恢复的操作；
- 完整 diff 中出现已确认范围之外的改动。
- 准备合并或正式发布（传入 `--signal pre_merge_or_release`）。

## 轻量处理顺序

1. **批量实现**：在已确认范围内一次性完成合理的修改批次，不为了保持流程而拆成微小轮次。
2. **先审查完整 diff**：检查正确性、范围、无关用户改动、回归风险和自动升级信号。发现问题时进入修复循环，修复后必须再审查完整 diff。
3. **再做最终定向验证**：只在最新一轮完整 diff 审查无阻止问题后，运行受影响的测试、构建、类型检查或人工验收步骤。
4. **修复总上限为 2 次**：初次实现不计入；因 diff 审查或验证失败而做的每个修正批次计 1 次，整个任务合计最多 2 次，不是每个验收项各 2 次。最终验证失败后如仍有余额，修正后必须回到步骤 2；用完 2 次仍不满足时停止，输出明确卡点。
5. **只在终点记录一次**：不在每轮同步交付日志、完成标准和状态文件。成功或停在明确卡点时，一次性记录最终 diff、修复次数、验证命令与结果、未完成项。

## 完整检查顺序

- 按完成标准实现，可在开发中运行受影响的快速检查，但不将它们冒充为最终结果。
- 在最终完整验证前，必须先对完整 diff 做问题优先审查：正确性、越界、产品一致性、项目基本规则和残余风险。审查导致修改后，重新审查 diff，再运行最终完整验证。
- 验收结果只能来自真实执行，并与当前最新代码对应。人工验收无法由 agent 判定时，如实列为“需人工确认”。
- 不得修改验收标准、阈值、必须通过标记或删除测试来换取通过。标准本身有问题时，提出修订并等待用户确认。

## 共同安全边界

- 本命令授权范围内的本地代码修改、本地测试构建以及范围明确时的本地 commit。
- **不授权** push、release、部署、数据库写入、生产配置写入、对外发送或任何不可逆操作。
- 不得声称未真实执行的测试、构建、截图、部署或审查已通过。

## Required Outputs

- 轻量处理：终点简报，包含处理方式、改动范围、最终 diff 审查、修复次数、真实验证结果、需人工确认项和明确卡点。不创建多份过程文档。
- 完整检查：在终点批量更新 `features/{feature}/交付至完成.md`、完成标准中的验收结果与 `00-工作流状态.md`；不为了状态同步而重复写入相同信息。
- 明确卡点的固定内容：缺什么（凭据/决策/环境/信息）、为什么需要、已尝试什么、可选的解除路径。

## 内部兼容详情

完整检查的现有文件可继续使用 `Oracle`、`blocking`、`NOT_RUN/PASS/FAIL/STALE/WAIVED` 作为机器字段。默认用户输出只显示“验收项/必须通过/未检查/已通过/未通过/改动后需重查/已确认跳过”。
